## 一、Workflow Loop / Graph 設計說明

### 1. 流程圖（Graph）

```text
[1. 取得原始資料 (raw_sources/ 5篇)]
          │
          ▼
[2. Ingest 解析與寫入 Wiki (wiki/ 6篇)] ◄───────┐ (若格式/雙向連結缺失則重寫)
          │                                       │
          ▼                                       │
[3. 數值與食安強制查核 (Fact-Check Gate)] ────────┘
    ├─ 檢查項目 A：°F / °C 單位是否統一且換算正確？
    ├─ 檢查項目 B：舒肥溫度是否附帶「維持時間前提」？
    └─ 檢查項目 C：牛排 vs. 禽肉安全標準是否隔離？
          │ (查核通過)
          ▼
[4. 整理簡報大綱 & 1對1 Wiki 溯源映射]
          │
          ▼
[5. 產生教學型 HTML 簡報 (presentation/index.html)]
          │
          ▼
[6. 自動化程式檢查 + 視覺渲染驗收] ◄── (若發現 JS 錯誤/破版/數據漂移則退回步驟 5 修正)
```

### 2. 哪些步驟會重複執行（Loop）？
- **Ingest → Fact-Check Loop（步驟 2 ↔ 3）**：每吸收一篇原始資料並產出 Wiki 條目後，會立即進入「強制查核區」驗證。若發現單位未換算、缺少時間前提或雙向連結斷裂，會退回步驟 2 補齊後再放行。
- **HTML 生成 → 檢查驗收 Loop（步驟 5 ↔ 6）**：產出 `index.html` 後執行 `check_web_app.py` 檢查 DOM ID、按鈕事件與無效連結，若有 Error/Warning 即退回修正並重驗。

### 3. 為什麼這樣設計？
將 **Fact-Check Gate（數值與食安查核）** 設為「進入簡報製作前」的關卡，並要求每篇 Wiki 設立「強制查核區」與 YAML `source` 欄位，可以確保簡報製作階段只讀取**已經過單位統一與前提補全**的乾淨知識，避免錯誤在生成 HTML 卡片時被放大或美化包裝。

## 三、反思（Reflection）

1. **哪一個節點最常出錯？**
   - **「整理重點／摘要生成」節點**最常出錯。因為 LLM 在將長篇 Wiki 濃縮成簡報卡片或表格時，會本能地追求「精簡字數」，極易把看似修飾語的**關鍵前提（如：維持 27.5 分鐘、達到核心溫度後起算）**刪掉，或是在不同熟度/物種間切換時發生 `°F / °C` 數值張冠李戴。

2. **發現問題後，把檢查往前移到了哪一個步驟？**
   - 原本我們是在「產生簡報 HTML 後」才進行人工閱讀檢查（Post-check），發現這樣一旦出錯就要重改 HTML 結構與互動腳本，成本很高。
   - 發現問題後，我們把檢查往前移到 **「Ingest 寫入 Wiki 時」與「查詢 Wiki → 整理簡報大綱之間」**，並在 `WIKI_RULES.md` 直接規定每篇 Wiki 必須內建 `## 關鍵數據與條件（強制查核區）`。

3. **有沒有因此修改 Workflow / Graph？為什麼？**
   - **有修改**。我們將原本線性的 `取得資料 → 寫入 Wiki → 產生簡報 → 最後檢查`，修改為在步驟 3 插入一個獨立的 **`Fact-Check Gate`（強制查核節點）**，並加上回退迴圈（Loop）。這樣做能把「知識正確性」與「視覺排版」解耦，讓問題在純文字階段就被低成本攔截，確保最終呈現給初學者的教學簡報既易懂又零食安風險。
